# ContainerToDrive.Desktop

Native WPF .NET 10 desktop/tray frontend. It references the Core/Windows projects plus pinned Azure Resource Manager, Blob Storage, and identity APIs for explicit browser sign-in and resource discovery.

## Integration contract

- Inherits the root target framework, nullable, implicit-usings, and warnings-as-errors settings.
- References the separately implemented Windows project and its `AppPaths.ResolveDataRoot(args)`, `AppPaths.IsElevated`, and `ControllerClient` APIs.
- The desktop launches no mount workers and communicates only through typed controller requests. It launches Explorer only with a validated single drive letter, using the Windows-directory executable.
- The controller executable and dependencies must be deployed where the Windows client expects them; a desktop-only build does not arrange controller packaging. Use the repository packaging workflow to keep the separate desktop/controller runtimes and engine manifest aligned.
- `--minimized` starts with only the notification-area icon. Arguments are passed to the agreed data-root resolver, never to a shell or a mount engine.

## Safety and behavior

- Closing the main window hides it to the tray by default. The saved close-to-tray preference can instead route closing through explicit exit, which obtains current status and confirmation. It requests controller shutdown only if every reported mount is unmounted and no recovery or missing profile status makes that uncertain. Otherwise exit closes only the UI.
- **Settings** groups Startup & window, Storage, Display & activity, New connection defaults, Connection settings, Components, and Privacy. Validated preferences use an explicit save/reset draft and the current root's DPAPI-protected settings store. Missing preferences use existing defaults without creating data; unreadable/unsupported preferences are preserved and saving is disabled. The existing startup, relocation, and connection handlers retain their safety guards and separate confirmation/persistence paths. See [Settings](../../docs/QUICKSTART.md#settings) for supported options and scope.
- **Start with Windows**, in **Settings > Startup & window**, is an opt-in setting for the current Windows user. It registers the current desktop executable in `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` with quoted `--minimized --data-root` arguments, preserving this instance's profile directory. At sign-in the app stays in the tray and starts its controller, which attempts only connections already configured for automatic mounting and skips uncertain recovery. This does not change any connection's auto-mount choice or bypass expired credentials, missing prerequisites, Windows Startup Apps policy, or recovery confirmation. Disabling the setting removes only a matching registration for this executable/data root and does not stop running drives. Changing the setting is disabled in elevated sessions; enabling requires the desktop executable and paired assembly to exist. Re-enable from the new location after moving a portable app. No registration is written without the user's checkbox action.
- `Status`, dialogs, and user operations share one asynchronous request gate. The poll loop awaits each request and then delays five seconds; no overlapping timer callbacks perform I/O. Requests have cancellation and bounded transport waits. A cancelled or timed-out controller mutation can still complete; the user is told to refresh before retrying.
- A separate two-second display clock expires old observations while network work is pending; it never sends controller requests. Dashboard operations and credential dialogs expose cancellation of their local wait.
- **Logs**, directly below Diagnostics, shows the latest 500 session events, newest first: frontend startup, backend connectivity transitions, and controller request outcomes with severity and request IDs. Successful status polling does not fill the log. Entries use fixed operation labels, never raw requests, responses, credentials, or exception text. Logs remain in memory; clearing them does not modify files, caches, or running drives.
- The Connections page shows the frontend, backend, actual live engine-worker count, and WinFsp installation evidence. Stale controller snapshots make backend/dependency status unknown rather than implying that processes stopped.
- **Activity & recovery** adds OxyPlot 2.2.0 history and traffic-share charts, connection/period filters, an accessible numeric table, period counters, recorded lifetime bytes, and expiring live rates. Connection activity cards retain their existing upload/recovery controls and add lifetime transfer counters. The controller, not the UI, samples and persists numeric-only history about every 15 seconds. Hourly/daily retention is 48 hours/366 days, with lifetime totals kept separately. UTC gaps, retries, incomplete history, and the lack of a directional/billing/delivery guarantee are explicit. Wire protocol 5 separates bounded history reports from lightweight status summaries. See [transfer statistics](../../docs/QUICKSTART.md#transfer-statistics) for persistence and sampling limits.
- The folder button in **Settings > Storage** uses the native Windows folder picker. A confirmed, idle, non-elevated controller verifies a copy to an empty local NTFS folder, re-protects root-bound settings, and commits a per-user root redirect only on success. The app reopens with the selected root; the original is retained. Mounted, missing, or recovery-required states disable the action. Partial copies remain on failure without source deletion; users are directed to check the active location before retrying. See [data folder selection](../../docs/QUICKSTART.md#choose-the-application-data-folder).
- **Test capabilities** checks authenticated controller access, pinned engine startup/version, local Windows mount support, WinFsp installation evidence, session elevation, drive-letter availability, and a temporary application-storage write. It does not mount drives or test Azure access/write permissions. Each result is shown with the last test time.
- Capability results expand on completion and collapse automatically after ten seconds by default. Settings also offers 30/60 seconds or Keep open. The last-test summary remains visible; expanding it restores the retained results without rerunning the checks or starting another collapse timer. A new test resets the countdown when it completes.
- Connection cards use two equal-width columns when the connection list can fit two 480-DIP cards plus spacing, and flow into one column in narrower windows. Additional connections wrap onto new rows. Source, mount state, upload/recovery warnings, and actions remain visible in a compact layout. Authentication, observation time, cache usage, and credential expiry are available under **Details**. Secondary icon actions retain accessible names and tooltips; mount, disconnect, and test remain labeled.
- Connection cards and Activity also show DNS-resolved host IPs with inferred **Private endpoint (DNS)** / **Public endpoint (DNS)** labels. Mixed, reserved, unavailable, and stale results remain explicit. All IPs and the timestamp are available under Details and in a tooltip explaining that DNS does not verify Azure Private Link or the worker's active TCP peer. DNS runs independently of controller polling with bounded concurrency/timeouts, per-host caching, manual refresh invalidation, and cancellation on interface stop; no Azure API is called, no new IPC fields are needed, and IP observations are not persisted or exported.
- **Install dependencies** is available only with a current, non-elevated controller snapshot, missing dependencies, and confirmed idle drives. Downloads use the embedded pinned manifest, approved HTTPS redirect hosts, size/time limits, and SHA-256 verification. A missing engine can be installed under `%LOCALAPPDATA%\ContainerToDrive\dependencies`; packaged/workspace engines remain preferred. The verified WinFsp MSI opens in Windows Installer after explicit confirmation, without silent installation or automatic restart. No cache cleanup is performed.
- The controller must return an explicit `MountStatus` for every saved profile, including unmounted profiles. Missing entries mean unknown, never implicitly safe/unmounted. Settings and removal remain disabled for missing, active, or recovery states.
- Worker timestamps determine telemetry freshness. Counts are observations, not proof that open files have reached Azure. Raw controller messages, exception text, and upload filenames are not rendered or logged.
- New profiles default to read-only with automatic mounting off, a 10 GiB cache target, and a 5 GiB free-space reserve. Saved cache/reserve preferences apply only to new connections; existing connections and clones are not changed. Writable access still requires visible risk acknowledgment before save. Available D–Z letters exclude current Windows drives and other saved profiles. The controller must recheck conflicts and validate all safety rules before mounting.
- Test & save sends `Validate` then `Save` sequentially. Test only clears the secret and asks for it again before a new/replacement-credential save. When editing without a replacement, `Validate(ProfileId)` checks the saved source; `Save(Profile)` validates updated settings. Existing IDs and revisions are preserved, and new revisions are zero. Changing the endpoint/container requires a new profile. Settings editing is intentionally stricter than the controller: clean, unmounted profiles only.
- Each connection card has **Test** and **Clone** actions. Test uses `Validate(ProfileId)` with the protected saved credential and a transient listing worker; it does not mount or write to Azure, and success does not prove write permission or access to every blob. Clone sends only the source profile ID to the controller, which assigns a unique copy name, fresh ID/revisions, and an available D-Z letter excluding Windows drives and all saved profiles. Settings and authentication are preserved, the credential is protected again for the new ID, and automatic mounting is forced off. The clone starts unmounted without copying cached files, workers, or recovery intent. The original is unchanged. No available drive letter or invalid saved credential prevents creation. Both actions require a current controller connection and no pending UI action, and their outcomes appear in the session log.
- SAS values and account keys appear only in `PasswordBox` controls or transient generated/request strings. Fields are cleared at request capture/completion and on close. Entra uses browser authentication and a memory-only desktop credential session; the generated delegation SAS follows the same protected controller path. Managed strings and transport serialization cannot promise perfect memory zeroization. No clipboard writes, credential logging, account-key retrieval, or file-transfer implementation is present in the desktop.
- The compact Add/Edit dialog has searchable subscription, resource-group, storage-account, and container dropdowns. Typing filters scoped, cached results by case-insensitive substring after a 250 ms debounce. Storage accounts are scoped to the selected subscription, narrowed by a resource group only when one is selected. Containers require a selected storage account and are listed only from that account. Changing a parent clears dependent selections and cancels stale searches; refresh reloads that scope. Each dropdown shows its own loading, empty, or safe failure state, with a 60-second search timeout and the existing 2,000-item discovery limit. Account-key container choices are also searchable after loading and are cleared when the account name changes.
- Writable controls require the controller feature flag and explicit risk consent. Recovery requires a separate consent before `Mount(Confirm=true)`. Risky immediate stop uses both `Force=true` and `Confirm=true`; ordinary disconnect uses neither.
- Elevated sessions cannot mount or start dependency setup from this UI and do not launch a controller; they may only try to inspect an existing one. The executable requests `asInvoker`. Explicit WinFsp setup may request administrator approval through Windows Installer; the desktop itself is not elevated and no UAC bypass is attempted.
- Diagnostic export displays the controller-returned absolute local path for manual review. It does not open or upload it. Protected file creation and redaction are controller responsibilities.
- Application and third-party license notices remain in the distribution's license files.

## Runtime validation

The [test documentation](../../tests/README.md) distinguishes unit, local integration, and interactive presentation checks. Remaining production-oriented runtime checks include:

1. Compile with the root .NET 10 SDK and warnings-as-errors; resolve the Windows project reference and stage the controller through the owning build/packaging project.
2. Exercise both missing-prerequisite and ready states; reject elevated mounting without attempting an elevation workaround.
3. Test empty profiles, missing mount entries, stale worker observations, offline controller, request timeouts, concurrent UI instances, and stale revision rejection.
4. Use synthetic SAS, account-key, and Entra delegation credentials to verify test-only clearing, discovery bounds, test-and-save, renewal identity/revision rejection, and no credential appearance in UI errors or logs.
5. Verify normal disconnect, pending uploads, explicit risky stop, recovery consent, close-to-tray, `--minimized`, exit with mounts, shutdown refusal, and reopening after a UI crash. Do not use production data for writable tests.
6. Test actual keyboard traversal, access keys, Narrator, high contrast, long names, 100/150/200% scaling, multi-monitor DPI, and small work areas. Standard window chrome and dynamic high-contrast colors are provided; runtime accessibility and visual certification are not claimed.

The window uses a vector application icon; the tray currently uses the Windows information icon. Signed packaging and full multi-resolution asset review remain release work. Light styling, Windows high contrast, and opt-in Windows sign-in startup are supported; a separate dark palette is not implemented.
